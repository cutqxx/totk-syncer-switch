# totk-syncer-switch

Утилита для Nintendo Switch (.nro) для синхронизации сохранений The Legend of Zelda: Tears of the Kingdom с Яндекс Диском через WebDAV.

Сейчас реализована **Фаза 0 (upload spike)**: приложение загружает тестовый файл `sd:/switch/totk-sync/test.zip` на Яндекс Диск через WebDAV PUT и показывает HTTP-код, код curl, время и число отправленных байт. Цель — проверить на реальном железе, работает ли загрузка там, где JKSV падает с curl 56.

## Установка тулчейна (Windows)

1. Установите [MSYS2](https://www.msys2.org/) в `C:\msys64`.
2. Подключите pacman-репозитории devkitPro в MSYS2 и установите пакеты:

   ```
   pacman -S switch-dev switch-curl switch-zlib
   ```

   (инструкция devkitPro: https://devkitpro.org/wiki/devkitPro_pacman). Тулчейн должен лежать в `/opt/devkitpro`.
3. Для хостовых тестов нужен gcc из MSYS2 UCRT64: `pacman -S mingw-w64-ucrt-x86_64-gcc make`.

## Сборка

Путь проекта может содержать пробелы и кириллицу, а Makefile devkitPro этого не переносит. Поэтому используйте `build.ps1`: он монтирует проект на свободную букву диска (T..Z) через `subst`, запускает make и снимает подстановку.

```
pwsh -File build.ps1 nro     # собрать totk-sync.nro
pwsh -File build.ps1 test    # хостовые тесты (gcc UCRT64, без devkitPro и сети)
pwsh -File build.ps1 clean
```

Из оболочки MSYS2 в каталоге без пробелов работают напрямую `make` (после `source /etc/profile.d/devkit-env.sh`) и `make test`.

Не кладите `config.json` в корень репозитория: шаблон Makefile libnx принимает его за конфиг NPDM. Свой конфиг держите на SD-карте.

## Что положить на SD-карту

| Файл | Куда |
| --- | --- |
| `totk-sync.nro` | `sd:/switch/totk-sync/totk-sync.nro` |
| `config.json` (по образцу `config.example.json`) | `sd:/config/totk-sync/config.json` |
| `test.zip` (любой файл от 1 байта до 64 МБ) | `sd:/switch/totk-sync/test.zip` |
| `ca.pem` (необязательно) | `sd:/switch/totk-sync/ca.pem` |

В `config.json` укажите логин Яндекса и **пароль приложения** (не основной пароль). Пароль не выводится на экран и не пишется в лог. Поле `keep_backups` принимается и игнорируется. `origin` должен начинаться со строчных `https://` (например, `https://webdav.yandex.com`).

### Какой конфиг используется

1. Если есть `sd:/config/totk-sync/config.json`, берётся он. Если он есть, но содержит ошибку (битый JSON, пустое или слишком длинное поле, `origin` не `https://`), приложение покажет эту ошибку и **не** переключится на JKSV.
2. Только если `config.json` не найден, берётся запасной `sd:/config/JKSV/webdav.json`. К его `basepath` дописывается `/The Legend of Zelda Tears of the Kingdom` (пустой `basepath` допустим, лишние `/` в конце убираются).
3. Если нет ни одного файла, на экране сообщение с обоими путями, загрузка (A) отключена.

На экране в строке `Config` всегда указан путь и источник (`totk-sync` или `fallback, from JKSV`). Только `https://`: HTTP без TLS не принимается. Ошибка разбора JSON показывается со строкой и столбцом.

### Если проверка сертификата падает (curl 60 или 35)

Проверка TLS никогда не отключается. Если системных корневых сертификатов Switch не хватает, положите PEM корневого CA Яндекса в `sd:/switch/totk-sync/ca.pem`: приложение передаст его в `CURLOPT_CAINFO` и покажет на экране, что используется ca.pem. Корневой сертификат можно взять из цепочки сертификатов `webdav.yandex.com` (браузер, экспорт в формате PEM; нужен корневой, а не конечный сертификат) или из набора CA Mozilla (`cacert.pem` с curl.se).

## Лог

Каждая попытка загрузки дописывает запись в `sd:/switch/totk-sync/log.txt` (каталог создаётся при отсутствии). В записи: время, имя варианта эксперимента (например, `com|noexpect|cl|t120`), URL, размер файла, HTTP-код, код и текст curl, время в секундах, отправленные байты, затем заголовки запроса и ответа. Тело файла в лог не пишется. Пароль в лог не попадает: значение заголовка `Authorization` заменяется на `***`, а пароль и base64 от `логин:пароль` вырезаются из всей записи. Если записать лог не удалось, загрузка всё равно выполняется, а на экране один раз показывается `Log unavailable`.

## Использование

Запустите приложение из hbmenu. **A** - загрузить `test.zip` (в Яндекс Диск попадёт новый файл `spike_<ГГГГММДД-ЧЧММСС>.zip`), **+** - выход. Загруженные файлы удаляйте вручную через веб-интерфейс Диска.

Варианты запроса переключаются без пересборки (на экране показаны текущие значения, адрес `Target` обновляется сразу):

| Кнопка | Что переключает |
|---|---|
| **X** | сервер: `.com` <-> `.ru` (если в конфиге другой origin, первое нажатие даёт `.com`); меняется только origin, путь и имя файла те же |
| **Y** | Expect: 100-continue вкл./выкл. (по умолчанию выкл., отправляется `Expect:`) |
| **L** | тело: Content-Length <-> chunked (`Transfer-Encoding: chunked`) |
| **R** | таймауты: обычные 15/120 с <-> длинные 30/600 с |

При каждом запуске приложения выбран вариант по умолчанию: сервер из конфига, Expect выкл., Content-Length, обычные таймауты. Выбор не сохраняется. Проверка TLS включена во всех вариантах.

Встроенная библиотека JSON: [cJSON](https://github.com/DaveGamble/cJSON), тег v1.7.18, лицензия MIT (`third_party/cjson/`).

## Предупреждения перед запуском на железе

- Во время загрузки приложение не реагирует на кнопки, включая HOME: до ~4 минут с обычными таймаутами и до ~20 минут с длинными. Дождитесь результата.
- Весь интерфейс и `log.txt` на английском: шрифт консоли libnx не содержит кириллицу и показывает её мусором. Коды HTTP и curl всегда ASCII.
- Имя файла в строке `Target` - пример. Реальное имя берётся в момент нажатия **A**.
- Переключение параметра перерисовывает и очищает экран: сначала перепишите результаты или смотрите их в `log.txt`.
- Берите `test.zip` не меньше 1 МиБ, лучше похожий по размеру на настоящий zip сохранений TotK из JKSV (~5-20 МБ), чтобы вариант «Expect вкл.» был показательным. Реальный заголовок Expect проверяйте в `log.txt`.
- Для `ca.pem` сначала попробуйте один корневой сертификат. Полный набор `cacert.pem` с бэкендом libnx не проверялся; при проблеме будет curl 77.

## Фаза 0 - результаты экспериментов

Как пройти матрицу: запустите приложение, для каждой строки таблицы выставьте варианты кнопками X/Y/L/R, нажмите **A**, перенесите из строки результата (и из `log.txt`) HTTP-код, код curl, время и отправленные байты в таблицу, сделайте вывод. Имя варианта в строке результата и в логе совпадает с выбранными кнопками.

Сборка (git SHA): `5241176` (Switch, Wi-Fi, 2026-11-03)

| вариант | ожидаемый тег | HTTP | curl | время | отправлено байт | вывод |
|---|---|---|---|---|---|---|
| по умолчанию, 13 МБ, попытка 1/2 | `com\|noexpect\|cl\|t120` | 0 | 56 | 12,0 с | 49 151 / 13 370 354 | обрыв в начале передачи (как у JKSV) |

| длинный таймаут (R), 13 МБ | `com\|noexpect\|cl\|t600` | 0 | 28 | 600,0 с | 13 370 354 / 13 370 354 | ответа нет за 600 с; файл на Диске побайтно совпадает |

| Expect вкл. (Y) | `com\|expect\|cl\|t120` | | | | | не прогонялся |
| .ru (X) | `ru\|noexpect\|cl\|t120` | | | | | не прогонялся |

### Правило решения: основной путь / fallback §8

Если вариант по умолчанию даёт 2xx `SUCCESS` и размер файла на Диске совпадает с test.zip → основной путь (фазы 1-2). Если все варианты, включая .ru, chunked и длинный таймаут, стабильно дают curl 56 (как JKSV) → fallback §8. Если проходит только неосновной вариант → основной путь, этот вариант становится профилем по умолчанию в Фазе 1.

Решение (2026-11-03): **ни прямой Яндекс, ни rclone — синхронизация напрямую с ПК по локальной сети.**

Выводы прогона:
- Загрузка со Switch на Яндекс по WebDAV технически проходит: все загруженные файлы на Диске побайтно совпадают с исходными, в обоих режимах тела (Content-Length и chunked).
- Но ответ сервера идёт слишком долго или не приходит вовсе: для 1 МБ — 201 через 64,6 с, для 13 МБ — нет ответа даже за 600 с. Иногда соединение рвётся в начале передачи (curl 56), как у JKSV.
- DNS не причина: соединение и проверка TLS-сертификата проходят, тело уходит целиком.

Облако в схеме было только посредником, поэтому оно убрано. Новая схема: лаунчер на ПК запускает игру, работает с сохранениями и, пока открыт, отдаёт и принимает сейв по HTTP в локальной сети (свой простой API, доступ по токену, IP ПК в конфиге на Switch). Копия в Яндекс Диск не делается. Новый план описывается отдельным спеком.

## Чек-лист проверки на железе

Отметьте после прогона на Switch.

Экран и запуск:
- [ ] .nro запускается из hbmenu и показывает origin, логин, полный URL назначения и подсказки кнопок (`A - upload test.zip`, `+ - exit`).
- [ ] Пароль не отображается на экране ни в каком виде.
- [ ] На экране видно, какой файл конфига использован (`totk-sync` или `fallback, from JKSV`).
- [ ] На экране меню видны текущие параметры эксперимента и кнопки их переключения.
- [ ] При запуске приложения параметры сброшены на значения по умолчанию.
- [ ] По **+** приложение без зависания возвращается в hbmenu.

Загрузка:
- [ ] По **A** файл `test.zip` загружается; в строке результата есть HTTP-код, код curl с текстом, время в секундах и число отправленных байт.
- [ ] Критерий фазы: при настройках по умолчанию ответ 201/204 и на экране `SUCCESS`.
- [ ] Файл виден в `JKSV/The Legend of Zelda Tears of the Kingdom/` на Диске и совпадает по размеру с test.zip.
- [ ] Строка результата и запись в `log.txt` содержат имя варианта (например, `com|noexpect|cl|t120`).
- [ ] Таблица результатов заполнена минимум для пяти вариантов, записано решение.

Ошибки:
- [ ] Каждая попытка (1/2) выводит свою строку результата, повтор не скрывает первую неудачу.
- [ ] Неверный пароль в config.json → `Wrong login/password (401)`, приложение остаётся в меню.
- [ ] Без сети (авиарежим) → понятная ошибка не позже чем через ~2 × 120 с + пауза, приложение не зависает и остаётся в меню.

Дополнительно:
- [ ] Локальное время в имени `spike_...` верное (не UTC).
- [ ] Строка CA показывает, какой источник используется (ca.pem или системные).
- [ ] Выход по **+** работает.
- [ ] Теги вариантов есть в `log.txt`.
