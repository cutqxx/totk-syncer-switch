# contracts/

Shared test vectors for the C code (Switch) and the C# code (PC launcher).
Expected values are produced independently of the launcher code.

## save-tree/

Reference TotK save layout with tiny files, plus junk files that must be ignored:
`desktop.ini`, `Thumbs.db`, `.nx_save_meta.bin`, `x.zip` at the root and `picturebook/THUMBS.DB`.

`picturebook/` contains names whose order depends on the byte order of `-`, `.`, `/`, `_` and upper/lower case:
`B.dat`, `a-b.dat`, `a.dat`, `a/b.dat`, `a_b.dat`.

The `album/` directory of a real save is empty, and git cannot store empty directories.
It is deliberately NOT in this tree (a placeholder file would change the fingerprint and file list).
Tests that need an empty `album/` create it with the test helper `SaveTreeBuilder` (directories do not affect the fingerprint).

## save-tree.fingerprint.txt

`sha256:<hex>` of `save-tree/` per the spec definition (SHA-256 over `<relative path with />\n<hex sha256 of content>\n`
for every non-junk file, sorted by path as UTF-8 bytes, lowercase hex).

Regenerate with the independent script (no launcher code involved):

```
python -I contracts/fingerprint.py contracts/save-tree > contracts/save-tree.fingerprint.txt
```

Cross-check with plain shell tools (run inside `contracts/save-tree`):

```
find . -type f ! -iname desktop.ini ! -iname thumbs.db ! -iname .nx_save_meta.bin ! -iname '*.zip' | sed 's|^\./||' | LC_ALL=C sort \
  | while read -r f; do printf '%s\n%s\n' "$f" "$(sha256sum "$f" | cut -d' ' -f1)"; done | sha256sum
```

Both must print the same hex as the txt file. Files here are stored byte-exact (`contracts/** binary` in `.gitattributes`).

## api/

JSON examples of launcher responses, written by hand from the spec "API" section (not generated by launcher code).
The PC test serializes its response DTOs and compares them JSON-equivalent to these files; the Switch test parses them.
All responses also carry the header `X-TotkSync-Api: 1` (Switch uses it to tell a launcher from a foreign server).

- `status-ok.json`, `status-never-synced.json`, `status-no-save.json`, `status-game-running.json`: `GET /status` (200). Dates have second precision and a UTC offset.
- `error-unauthorized.json` (401), `error-forbidden.json` (403), `error-not-found.json` (404, unknown path), `error-method-not-allowed.json` (405), `error-internal.json` (500, unexpected launcher error; no details in the body).

## switch-config.example.json

Образец файла, который лаунчер сохраняет как `switch-config.json` (на SD он лежит как `sd:/config/totk-sync/config.json`).
Switch (`switch/source/core/config.c`) принимает этот файл как есть, а также вариант с CRLF и с UTF-8 BOM (BOM срезается до разбора).

Правила проверки на стороне Switch (одинаковые с ПК там, где ПК тоже проверяет):

- `pc_host`: ровно 4 десятичных октета 0-255 через точку, без ведущих нулей (`192.168.01.10` отклоняется, чтобы не получить восьмеричную трактовку `inet_aton`), без пробелов и знаков. Разрешены только частные диапазоны `10/8`, `172.16/12`, `192.168/16`. **`127/8` отклоняется**, как и в `switch-config.json` на ПК. Имена хостов и IPv6 не поддерживаются.
- `pc_port`: JSON-число, целое, 1024-65535 (строка `"8765"` отклоняется).
- `token`: непустая строка из печатных ASCII-символов без пробелов, короче 128 символов. Пустая или состоящая из пробелов строка считается пустым полем. Жёсткой проверки «ровно 64 hex» нет: ПК всегда пишет 64 hex-символа, а Switch лишь гарантирует, что токен можно безопасно положить в заголовок `Authorization`. Очень короткий токен (несколько символов) при вырезании из лога и текстов экрана затронет и посторонний текст с теми же символами.
- `keep_backups`: необязательное целое не меньше 1, по умолчанию 20.
- Только поля Яндекса фазы 0 (`origin`, `username`, `password`, `basepath`) без новых полей: `Old Phase 0 config: save switch-config.json from the PC launcher`.

## Как Switch читает ответы лаунчера

- Заголовок `X-TotkSync-Api: 1` есть на всех ответах лаунчера, включая 401 и 403. Имя заголовка сравнивается без учёта регистра.
- Ответ без этого заголовка (с любым кодом, включая 200 и 401) считается ответом чужого сервера: `Not a TotK Sync launcher at <host>:<port>`.
- `200` дополнительно проверяется по JSON: `app == "totk-sync"` и `api == 1`, иначе тоже «не лаунчер».
- `401` с заголовком: `Wrong token: ...`; `403` с заголовком: отдельное сообщение про частную сеть; остальные коды с заголовком (в том числе `500 {"error":"internal"}`): `PC error: HTTP <код>`.
- Дата `save.modified` показывается как `YYYY-MM-DD HH:MM`, вырезанная из строки (локальное время ПК), без пересчёта по часам Switch.

## PUT /save (слайс 1.5)

Тело запроса: ZIP сейва как есть, `Content-Length` обязателен. Параметр `?force=1` заменяет сейв ПК даже при конфликте (бэкап всё равно делается).
Ответы (все с заголовком `X-TotkSync-Api: 1`):

| Код | Файл | Когда |
|---|---|---|
| 200 | `api/put-replaced.json` | сейв заменён, в ответе имя бэкапа и отпечаток |
| 200 | `api/put-unchanged.json` | отпечаток входящего сейва совпал с текущим сейвом ПК: бэкапа и замены нет, `last_sync` обновлён |
| 400 | `api/error-invalid-zip.json` | ZIP нарушает правила; `reason` из `save-zip/cases.json` |
| 404 | `api/error-no-save.json` | на ПК нет сейва (или `save_dir` указывает не на сейв) |
| 409 | `api/error-conflict.json`, `api/error-conflict-never-synced.json` | сейв ПК изменился после последней синхронизации (или истории нет) и входящий сейв отличается; `last_sync_at` равен `null`, если истории нет. С `?force=1` конфликта нет |
| 411 | `api/error-length-required.json` | нет `Content-Length` (в том числе chunked) |
| 413 | `api/error-too-large.json` | `Content-Length` больше 64 МиБ |
| 423 | `api/error-game-running.json` | запущен `totk.exe` |
| 503 | `api/error-busy.json` | уже идёт другая запись |
| 500 | `api/error-write-failed.json` | бэкап или замена не удались (сейв ПК не изменён), либо найдено несколько папок сейва, либо загрузка оборвалась |

Отказы 404/411/413/423 приходят до чтения тела (при `Expect: 100-continue` тело вообще не отправляется).

## save-zip/

Тестовые ZIP для правил «Валидный ZIP сейва». Создаются независимым скриптом (только стандартная библиотека Python, без кода лаунчера), результат детерминирован:

```
python -I contracts/save-zip/generate.py
```

`cases.json`: список `{file, valid, reason}`. Для валидных ещё `saved_files` и `saved_dirs`: что должно оказаться в папке сейва (без мусора и без `.nx_save_meta.bin`).
Тексты `reason` задаёт ПК, Switch показывает их как есть.

- `valid-save-tree.zip`: всё из `save-tree/` (с мусором) плюс пустой `album/`, без заглушки `.nx_save_meta.bin`; отпечаток после распаковки равен `save-tree.fingerprint.txt`. Заглушка не годится как мета-файл JKSV (чужой title ID).
- `valid-from-switch.zip`: тот же сейв (`save-tree/` плюс пустой `album/`), но собранный кодом Switch (`save_pack_dir`, miniz, `MZ_BEST_SPEED`, единая метка времени 2026-11-03 00:00:00). Создаёт его не `generate.py`, а хостовый тест Switch, в `cases.json` он стоит с теми же `saved_files`/`saved_dirs`, что и `valid-save-tree.zip`. ПК-тесты проверяют его так же, как остальные валидные архивы (verdict и список), и сверяют отпечаток с `save-tree.fingerprint.txt`: так проверяется, что валидатор лаунчера принимает именно то, что кладёт Switch. Тест Switch `the_committed_switch_zip_lists_the_same_entries_as_a_fresh_pack` сравнивает свежую упаковку с файлом по списку `{имя, каталог ли, CRC, размер}` (не побайтно, чтобы обновление miniz не ломало тест). Файл детерминирован: повторная упаковка даёт те же байты. Пересоздать после намеренного изменения формата ZIP:

  ```
  TS_REGENERATE_CONTRACT_ZIP=1 pwsh -NoProfile -File build.ps1 test
  ```

  (тест перезаписывает файл и сверяется уже с ним; затем нужно прогнать `pwsh -NoProfile -File build.ps1 pc-test`, чтобы убедиться, что ПК принимает новый архив).
- `valid-minimal.zip`, `valid-empty-dirs.zip`, `valid-junk-extra.zip`, `valid-jksv-meta.zip` (мета с title ID TotK).
- Неверные: `invalid-not-zip`, `invalid-crc`, пути (`abs-path`, `dotdot`, `dotdot-inner`, `backslash`, `drive-letter`, `stream-name`, `reserved-name`, `reserved-space-ext` (`CON .txt`), `reserved-spaces-ext` (`nul  .dat`), `trailing-dot`, `trailing-space`, `trailing-dot-dir`, `symlink`), дубликаты (`dup`, `dup-case`, `dup-dir-case`, `file-and-dir`), раскладка (`no-option`, `no-progress`, `wrapped-root`, `slot-out-of-range`), лимиты (`too-many-entries`: 1001 запись; `too-large`: 65 МиБ после распаковки; `compression-bomb`: 8 МиБ нулей в ~8 КиБ, reason `suspicious compression ratio`), мета (`meta-other-title`, `meta-bad-magic`).

Дополнительно к правилам спека лаунчер отклоняет символы `<>:"\|?*`, управляющие символы, имена с точкой или пробелом в конце любого сегмента пути, зарезервированные имена Windows (`NUL`, `CON`, `CONIN$`...), в том числе с пробелами перед расширением (`CON .txt`), записи-символические ссылки и конфликт «файл и каталог с одним путём». Сравнение путей без учёта регистра. Распаковка не доверяет заголовку размера: запись читается ровно на заявленную длину и не дальше, сумма заявленных длин не больше 64 МиБ, а при распаковке от 4 МиБ коэффициент сжатия не больше 200:1 (иначе `suspicious compression ratio`).
